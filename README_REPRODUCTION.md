# T10 WAF 실험 재현 방법

작성자 박지훈 / 정리일 2026-10-20

## 1 기존 결과를 검증하기

이 경로는 서버 설치나 인터넷 접속이 필요하지 않습니다. Windows에서도 Python 3 표준 라이브러리만 있으면 실행할 수 있습니다. 이 ZIP을 먼저 모두 압축 해제합니다.

```
python analysis/independent_verify.py original verification-output
```

예상 결과는 `requests=7200`, `audit_matched=7200`, `coverage_combinations=7200`, `paired_http_https=3600`, `paired_differences=0`, `repeat_changed=0`, `issues=[]`, `passed=true`입니다. `hash_files=30`은 사용자가 전달한 공개 사본의 내부 해시 목록 검증 수입니다. 일부 탐지 로그의 UTF-8 바이트가 유효하지 않으므로 분석할 때만 대체 문자로 디코딩합니다. `invalid_utf8_lines`는 PL1 20줄, PL2 80줄, PL3 780줄이며 JSON 구문 분석 실패는 0줄입니다. 원본 바이트는 변경하지 않습니다. 깨진 탐지 부분 문자열을 정확한 문자열 증거로 인용하지 마십시오.

`analysis/independent_verify.py`는 원본 사례 내용, 입력 해시, 실행기 해시, 공개본에 남긴 해시, 전체 조건과 10회 회차의 완전성, 요청 ID 중복, WAF 내부 경로와 q 값, PL, 응답, Host·User-Agent·Accept, 949110 차단 규칙 및 HTTP/HTTPS의 입력별 응답 일치를 확인합니다. 새 요청을 보내지는 않습니다. 파일 해시는 보존된 바이트의 일치 여부를 확인하며 외부 공증이나 조작 불가능성을 증명하지 않습니다.

## 2 새 Ubuntu 서버에서 실험 다시 실행하기

대상은 별도의 Ubuntu 24.04 amd64 실험 서버입니다. 기존 서비스가 있는 서버에는 bootstrap을 적용하지 마십시오. sudo 권한이 있는 ubuntu 계정에서 이 패키지를 압축 해제합니다. 메모리가 약 1 GiB이고 Swap이 없으면 설치 스크립트가 디스크 여유 공간 3 GiB 초과를 확인하고 2 GiB Swap을 만듭니다. 이 Swap은 재부팅 시 자동 활성화되지 않습니다.

AWS에서는 공인 IPv4와 인터넷 게이트웨이를 통한 접근이 가능한 서브넷을 준비하고 SSH 22, HTTP 80, HTTPS 443의 실습용 접근을 허용합니다. 18081~18083은 loopback 전용이므로 외부 개방하지 않습니다. 본 자동 실험은 AWS 보안그룹 경유 외부 왕복을 측정하지 않습니다. 외부 브라우저 접속 시연은 별도로 수행합니다.

```
bash reproduction/bootstrap_ubuntu.sh 현재_EC2_공인IPv4
python3 ~/t10-waf/run_main.py --rounds 10
```

공인 IPv4 자리에는 실제 숫자 주소를 넣습니다. bootstrap은 Nginx와 ModSecurity 패키지를 설치하고 제공된 CRS 규칙·설정을 복사하며 새 자체 서명 인증서를 발급합니다. 전용 실험 서버의 기본 사이트 링크를 해제하고 t10-public 사이트를 활성화합니다. 서버 개인키는 새로 생성되며 패키지에는 들어 있지 않습니다. 인증서와 실행기의 주소 부분이 바뀌므로 해당 해시도 원 실험과 달라집니다. 새 결과와 원 결과를 덮어쓰지 말고 별도로 보관하십시오.

기준 버전은 nginx 1.24.0-2ubuntu7.18, libmodsecurity3t64 3.0.12-1.1build2, connector 1.0.3-1build3, CRS 4.0.0, Python 3.12.3, curl 8.5.0입니다. apt 저장소의 현재 패키지를 설치하므로 패키지 버전이 달라질 수 있습니다. `dpkg-query -W nginx libmodsecurity3t64 libnginx-mod-http-modsecurity`와 `python3 --version`, `curl --version`을 기록하여 원 실험과 비교하십시오. 동일 버전의 OS 이미지·패키지 보관본은 이 ZIP에 포함하지 않았습니다. 버전이 다른 재실행은 별도 환경 재현으로 구분합니다.

브라우저에서는 `http://공인IPv4/` 또는 `https://공인IPv4/`로 접속합니다. 재현용 HTML은 원 서버 화면 파일이 아닙니다. 같은 /pl1/, /pl2/, /pl3/ 경로로 실제 요청을 보내고 HTTP 상태를 표시하는 대체 시연 페이지입니다. 정적 응답 페이지의 외관은 WAF의 요청 검사 판단에 사용되지 않습니다. 자체 서명 인증서의 브라우저 신뢰 경고는 암호화 여부와 구분하십시오. 자동 실행기는 새 인증서를 --cacert로 신뢰하고 IP 이름을 검증합니다.

원 실행기의 curl은 --connect-to로 URL의 공인 IP에 해당하는 연결을 127.0.0.1:80 또는 :443으로 연결합니다. HTTPS는 공개 Nginx에서 복호화되고 /plN/ 요청은 해당 내부 Nginx 서버로 HTTP 전달됩니다. 이 구성에서는 HTTP와 HTTPS 모두 동일한 CRS 요청 검사를 받습니다. TLS1.2/TLS1.3 허용 설정이지만 원 요청별 curl 기록상 실제 HTTPS 협상 세부 내용은 별도 TLS 캡처로 모두 검증한 것이 아닙니다.

## 3 새 실행의 원자료 보존

완료 메시지에 표시된 `~/t10-waf/results/실행번호/`가 새 결과 폴더입니다. responses.jsonl, manifest.json, cases_main.json을 보존하고 /var/log/nginx/t10-pl1-audit.jsonl부터 pl3까지의 원본을 같은 폴더에 복사하십시오. 감사 로그에는 다른 실험도 포함될 수 있으므로 X-T10-ID로 해당 실행 요청만 골라 비교합니다. 기존 original 폴더는 변경하지 마십시오. 새 서버 설치 시 다운로드되는 CRS 규칙은 별도 제공 해시로 확인합니다. 공개본에는 원 인증서가 없으므로 과거 인증서 해시 검증은 수행하지 않습니다.

기존 사용자의 inspect_results.py, analyze_categories.py, analyze_rules.py, verify_audit.py에는 원 실행 폴더가 고정돼 있습니다. 새 실행에 적용하려면 folder 경로를 바꾸고 verify_audit.py의 절대 사용자 경로도 확인해야 합니다. 이는 원 실행용 분석 스크립트이며 범용 인자가 있는 실행기로 가장하지 않습니다. original 원자료 검증에는 별도로 제공한 독립 검증기를 사용하십시오.

## 4 결과를 해석하는 범위

120개 문자열은 정상 60개와 공격 테스트용 60개입니다. 정상 60개는 기본 입력 30개를 두 가지 접두 문장으로 감싼 사례이므로 독립적인 정상 사례 60종이라고 보지 않습니다. wrapper_language=en은 영어 접두 문장을 뜻하며 본문 전체의 영어 여부를 뜻하지 않습니다. 10회 반복은 반복 일관성 확인이며 독립 표본을 10배 늘리는 것이 아닙니다.

정상 코드 설명을 문자로 받아 표시하는 업무 정책을 기준으로 정상 레이블을 정했습니다. 공격 레이블은 공격 특징을 담은 요청이라는 뜻이며 실제 SQL 실행·XSS 실행의 성공 여부는 검증하지 않았습니다. 전체 CRS가 활성화돼 있어 RCE·프로토콜 규칙도 SQLi/XSS 테스트 차단에 기여할 수 있습니다. 한글이나 HTML을 무조건 허용하도록 튜닝한 실험은 수행하지 않았습니다.

## 재현 및 통과 확인 네 가지

1. 원자료 무결성: 공개 목록의 30개 파일 SHA256과 공개 사본의 입력·실행기 manifest 해시 일치 인증서 제외.
2. 설계 완전성: 120개 입력 × PL 3개 × 프로토콜 2개 × 회차 10개 = 7,200개 조합이 각각 한 번 기록됨.
3. 실제 WAF 근거: 요청 ID로 감사 로그 7,200건이 각각 한 번 대응하고 PL·입력·응답·949110 기록이 일치함.
4. 반복·전송 조건: 720개 조건·입력 조합에서 응답 변화 0개, HTTP/HTTPS 대응 3,600쌍의 응답 차이 0개.
